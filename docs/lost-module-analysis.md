# Lost Module — Analysis

> Аналіз модуля пошуку загублених тварин. Фіксація архітектурних рішень та критичних моментів.
> 
> **⚠️ Примітка:** Поточна реалізація в БД (0002-setup-main-tables.xml) не обов'язково відповідає фінальним вимогам. Нижче описана **фінальна схема даних**.

## 1. Фінальна схема даних

### 1.1 lost_requests

| Колонка | Тип | Обов'язкове | Опис |
|---------|-----|-------------|------|
| id | BIGINT | PK | Ідентифікатор |
| pet_id | BIGINT | FK (unique) | Посилання на тварину |
| contact_info | VARCHAR(255) | NOT NULL | Контактні дані власника |
| last_seen_location | GEOGRAPHY(POINT, 4326) | NOT NULL | Геолокація останнього бачення |
| pet_type | VARCHAR(50) | NOT NULL | Денормалізація: тип тварини |
| search_text | TEXT | NOT NULL | Денормалізація: текст для pg_trgm |
| status | VARCHAR(50) | NOT NULL | ACTIVE, CANCELLED |
| created_at | TIMESTAMP | NOT NULL | З базової сутності |
| updated_at | TIMESTAMP | NOT NULL | З базової сутності |

**Що прибрано:**
- `owner_id` — не потрібен, отримуємо через `pet.owner_id`
- `photo_url` — беремо з `pets.photo_url`
- `description` — не потрібен, `contact_info` достатньо
- `resolved_at` — не потрібен, достатньо `status` + `updated_at`

**Індекси:**
- idx_lost_type (pet_type)
- idx_lost_status (status)
- idx_lost_location (GIST на last_seen_location)
- idx_lost_search_text (GIN на search_text з gin_trgm_ops)

**Чому денормалізація безпечна:**
- Pet зі статусом `IN_LOST` не можна редагувати
- Дубльовані дані генеруються один раз при створенні

**Каскадне видалення:**
- При скасуванні/видаленні `lost_request` — видаляються всі записи з `match_queue`, пов'язані з цією анкетою
- Статус `Pet` змінюється на `DEFAULT`

### 1.2 found_requests

| Колонка | Тип | Обов'язкове | Опис |
|---------|-----|-------------|------|
| id | BIGINT | PK | Ідентифікатор |
| finder_id | BIGINT | FK | Хто знайшов |

| description | TEXT | NOT NULL | Агрегований текст для пошуку (порода + колір + окрас + стать + ознаки) |
| created_at | TIMESTAMP | NOT NULL | З базової сутності |
| updated_at | TIMESTAMP | NOT NULL | З базової сутності |

**Примітки:**
- Анкети знахідки **не мають статусу**

**Індекси:**

### 1.3 match_queue

| Колонка | Тип | Обов'язкове | Опис |
|---------|-----|-------------|------|
| id | BIGINT | PK | Ідентифікатор |
| lost_request_id | BIGINT | FK | Анкета пошуку |
| found_request_id | BIGINT | FK | Анкета знахідки |
| score | NUMERIC(7,4) | NOT NULL | Відсоток співпадіння (0.0000 - 1.0000) |
| viewing_status | VARCHAR(50) | NOT NULL | NEW, VIEWED, REJECTED |
| viewed_by | VARCHAR(20) | nullable | OWNER або FINDER |
| created_at | TIMESTAMP | NOT NULL | З базової сутності |
| updated_at | TIMESTAMP | NOT NULL | З базової сутності |

**Примітка:** Таблиця використовується тільки для власників (lost). Для перехожих (found) — окремий in-memory кеш.

**Каскадне видалення:**
- При видаленні `lost_request` — автоматично видаляються всі пов'язані записи з `match_queue`
- При видаленні `found_request` — автоматично видаляються всі пов'язані записи з `match_queue`

## 2. Як працює модуль (архітектура та принципи)

### 2.1 Загальна концепція

Модуль з'єднує дві групи користувачів:
- **Власники** — подають своїх загублених тварин у пошук
- **Перехожі** — знаходять тварин на вулиці і додають анкети знахідок

Система автоматично порівнює анкети пошуку з анкетами знахідок і пропонує потенційні збіги обом сторонам.

### 2.2 Два типи анкет

**Lost Request (анкета пошуку):**
- Створюється власником на основі існуючої тварини з профілю
- Містить тільки контактну інформацію і геолокацію останнього бачення
- Текст для пошуку генерується автоматично з даних тварини (порода, колір, прикмети)
- Активна до моменту скасування власником
- Прив'язана до конкретного Pet (unique FK)

**Found Request (анкета знахідки):**
- Створюється будь-яким користувачем без прив'язки до профілю тварини
- Вимагає фото, геолокацію та текстові характеристики
- Додаткові поля (порода, колір, окрас, стать, ознаки) збираються окремо на різних кроках форми
- Усі текстові відповіді агрегуються в єдиний description для триграмного порівняння
- Тип тварини зберігається окремо як жорсткий фільтр (DOG/CAT/інше не змішуються)
- Одноразова — після перегляду рекомендацій стрічка закінчується
- **Живе 1 рік** з моменту створення, потім автоматично видаляється кроною

### 2.3 Дві різні стратегії стрічок

**Для власника (постійна стрічка):**
- Використовується таблиця match_queue в БД
- При створенні нової анкети знахідки система асинхронно шукає відповідні анкети пошуку
- Знайдені пари зберігаються в match_queue з рейтингом схожості
- Власник бачить постійно оновлювану стрічку всіх потенційних знахідок
- Можна відхилити рекомендацію, але повернутись до неї пізніше
- При перегляді власнику показується **дата створення анкети знахідки** (щоб розуміти актуальність)

**Для перехожого (разова стрічка):**
- Використовується in-memory HashMap з TTL 1 день
- При створенні анкети знахідки виконується одноразовий розрахунок 50 найкращих збігів
- Результат зберігається в кеші як список ID анкет пошуку
- Перехожий переглядає рекомендації поки черга не закінчиться
- Кожен перегляд видаляє елемент з кешу (FIFO)
- Якщо перехожий відмінив перегляд рекомендацій — більше їх побачити не зможе
- Коли кеш спорожнів або закінчився TTL — перехожий більше не може переглядати рекомендації

**Чому різні підходи:**
- Власник зацікавлений у постійному моніторингу нових знахідок
- Перехожий робить одноразову дію — знайшов тварину, перевірив чи шукають, більше не повернеться
- Кеш для перехожого дешевший і не засмічує БД

### 2.4 Асинхронний matching (через івенти)

При створенні нової анкети публікується івент, який запускає matching:
- Для нової found_request — шукаємо всі active lost_requests з тим самим pet_type, обчислюємо score, зберігаємо в match_queue для власників і в кеш для перехожого
- Для нової lost_request — шукаємо всі recent found_requests з тим самим pet_type, обчислюємо score, додаємо в match_queue

**Важливо:** matching — асинхронний процес через івенти. Користувач не чекає на результат, стрічки оновлюються у фоні.

### 2.5 Життєвий цикл анкети пошуку

1. **Створення:** Власник обирає тварину зі свого списку
   - Якщо тварини немає — натискає "Додати тварину" → запускається форма ADD_PET → після завершення повертає на меню початку пошуку
   - Якщо тварина є — заповнює контакт + геолокацію → статус ACTIVE
2. **Очікування:** Pet отримує статус IN_LOST (не можна редагувати дані тварини)
3. **Matching:** Система постійно шукає нові знахідки та додає в стрічку власника
4. **Перегляд:** Власник бачить рекомендації (фото знахідки, опис, відстань, **дата створення**)
5. **Знайдення:** Власник натискає "Це моя тварина" на відповідній анкеті
6. **Підтвердження:**
   - **Змінюється тільки геолокація тварини** — `pet.last_seen_location` оновлюється на локацію знахідки
   - Статус `lost_request` залишається ACTIVE
   - Статус `Pet` залишається IN_LOST
   - Скасування пошуку — тільки вручну власником
7. **Завершення:** Власник скасовує пошук → статус CANCELLED → видалення анкети

**Скасування:**
- Власник може скасувати анкету пошуку
- Статус змінюється на CANCELLED
- Статус Pet повертається на DEFAULT
- Всі записи з match_queue видаляються (каскадно)
- Анкета пошуку видаляється

### 2.6 Життєвий цикл анкети знахідки

1. **Створення:** Перехожий проходить форму з кроків (тип, фото, локація, порода, колір, окрас, стать, ознаки)
2. **Агрегація:** Усі текстові поля об'єднуються в description для порівняння, тип тварини зберігається окремо
3. **Matching:** Асинхронний розрахунок 50 найкращих збігів з lost_requests (фільтр по pet_type, потім similarity)
4. **Кешування:** Результат зберігається в HashMap на 1 день
5. **Перегляд:** Перехожий бачить по одній анкеті пошуку з контактами власників (якщо власник залишив контакт)
6. **Вичерпання:** Після перегляду всіх 50 рекомендацій стрічка закінчується
7. **Автоматичне видалення:** Через 1 рік після створення крона видаляє анкету (каскадно видаляються match_queue)

**Примітки:**
- Скасовувати `found_request` неможливо
- Перехожий може відхилити перегляд рекомендацій — після цього більше не побачить їх

### 2.7 Ключові бізнес-правила

- Тварина може мати тільки одну активну анкету пошуку (unique constraint на pet_id)
- При створенні анкети пошуку тварина переходить в статус IN_LOST і не може редагуватись
- Статус тварини можна змінити тільки при статусі DEFAULT
- Контактна інформація в lost_request надається власником окремо від даних тварини
- Геолокація в обох анкетах обов'язкова — без неї matching неможливий
- Алгоритм matching враховує тільки анкети в радіусі 50 км
- Тип тварини (pet_type) — жорсткий фільтр, різні типи не порівнюються
- Для перехожого стрічка формується один раз і живе 1 день
- Власник може відхилити рекомендацію і повернутись до неї пізніше
- При підтвердженні знахідки змінюється тільки геолокація тварини, статуси не змінюються
- При видаленні тварини — каскадно видаляються всі пов'язані анкети пошуку та записи в match_queue
- При скасуванні lost_request — статус Pet змінюється на DEFAULT, всі записи match_queue видаляються
- Перехожий може зв'язатись з власником тільки якщо той залишив контактну інформацію
- Рекомендації для власника та перехожого відправляються кожна новим повідомленням, у попереднього повідомлення прибирається клавіатура (аналогічно перегляду feed)
- Анкети знахідки живуть 1 рік, потім автоматично видаляються кроною

### 2.8 Крона очищення старих анкет

**Час запуску:** Щодня о 00:00

**Логіка:**
- Знаходить всі `found_request` з `created_at < NOW() - INTERVAL '1 year'`
- Видаляє їх каскадно (автоматично видаляються записи з `match_queue`)
- Опціонально: логування кількості видалених записів

**Причина:**
- Через рік можна з впевненістю сказати, що анкета не актуальна
- Очищення БД від застарілих даних

## 3. Алгоритм matching

- **Географічна складова (40%):** Лінійна шкала, 50км = 0%, 0км = 100%
- **Текстова складова (60%):** pg_trgm.similarity(lost.search_text, found.description)
- **Бонус:** Якщо found.description містить точні співпадіння з ключовими словами (порода, колір) — додаткові бали

## 4. Флоу створення анкет

### 4.1 Lost Request

**FormType:** CREATE_LOST_REQUEST — 2 кроки:
1. Контактна інформація (текст)
2. Геолокація останнього бачення

**Створення:** 
- Власник обирає тварину зі списку своїх тварин
- Якщо тварини немає — натискає "Додати тварину" → запускається форма ADD_PET
- Після додавання тварини — повернення на меню початку пошуку
- Збір через форму → генерація search_text з Pet → запис в БД

### 4.2 Found Request

**FormType:** CREATE_FOUND_REQUEST — кроки:
- Тип тварини (choice з PetType)
- Фото
- Геолокація
- Порода (текст, skippable)
- Колір (текст, skippable)
- Тип окрасу (текст, skippable)
- Стать (choice з PetSex, skippable)
- Розмір (choice з PetSize, skippable)
- Особливі ознаки (текст, skippable)

**Формування description:**
Після завершення форми всі текстові відповіді (порода, колір, окрас, стать, ознаки тощо) об'єднуються в єдиний description. Цей текст використовується для триграмного порівняння з lost_requests.search_text. Тип тварини (pet_type) зберігається окремо і використовується як жорсткий фільтр перед текстовим пошуком.
Якщо поле опціональне і його нема, ми просто не враховуємо його (не додаємо в текст).

## 5. Стрічки рекомендацій

### 5.1 Для власника (Lost → Found)

- **Джерело:** match_queue (постійно оновлюється)
- **Механізм:** При створенні found_request → асинхронний matching через івент → додавання в match_queue
- **Сортування:** за score DESC
- **Фільтр:** статус NEW або REJECTED
- **Відображення:** Кожна рекомендація — нове повідомлення, у попереднього прибирається клавіатура
- **Додаткова інформація:** Показується дата створення анкети знахідки (created_at)

### 5.2 Для перехожого (Found → Lost)

- **Джерело:** In-memory HashMap (user_id → список lost_request_id)
- **Механізм:** При створенні found_request → одноразовий батч (50 найкращих) → кешування
- **TTL:** 1 день, потім eviction
- **Поведінка:** При перегляді видаляється з кешу (FIFO)
- **Обмеження:** Якщо перехожий відхилив перегляд — більше не побачить рекомендацій
- **Контакти:** Перехожий бачить контакти власника тільки якщо той їх залишив
- **Відображення:** Кожна рекомендація — нове повідомлення, у попереднього прибирається клавіатура

## 6. UI / UX Вимоги

### 6.1 Збереження історії перегляду рекомендацій

При перегляді рекомендацій (для власника та перехожого):
- Кожна анкета виводиться з кнопками "Наступна" та "Повернутись"
- При натисканні **будь-якої** кнопки ("Наступна" або "Повернутись"):
  - З **минулого** повідомлення прибирається клавіатура (editMessageReplyMarkup з reply_markup = null)
  - Новий контент відправляється новим повідомленням (або редагується поточне для "Наступна")
- Це забезпечує збереження історії та уникає багів з "залишковими" кнопками в історії чату

### 6.2 Флоу "Я знайшов тварину" (для перехожого)

1. Користувач натискає "Я знайшов тварину"
2. Запускається форма CREATE_FOUND_REQUEST (всі кроки)
3. Після заповнення та підтвердження:
   - Відображається повідомлення: "Анкету збережено. Ми знайшли потенційних власників для цієї тварини."
   - Дві кнопки:
     - "Переглянути рекомендації" — виводить першу анкету з кешу
     - "Повернутись" — повернення до головного меню, **рекомендації стають недоступними назавжди**
   - Важливо проінформувати користувача: якщо він натисне "Повернутись", переглянути анкети буде неможливо

### 6.3 Флоу "Почати пошук" (для власника)

1. Власник натискає "Почати пошук"
2. Відображається **пагінований список** його тварин (як у "Мої Тварини"):
   - Кожна тварина — кнопка
   - Кнопка "Додати тварину" — запускає форму ADD_PET
3. Якщо користувач обрав "Додати тварину":
   - Запускається форма ADD_PET (вже існує)
   - Після завершення форми — **повернення на цей же список тварин**
   - Нова тварина з'являється у списку
4. Користувач обирає конкретну тварину зі списку
5. Ініціюється форма CREATE_LOST_REQUEST з `pet_id` вже заповненим
6. **Кроки форми:**
   - Контактна інформація (текст, обов'язкове)
   - Геолокація останнього бачення (обов'язкове)
   - Особливі ознаки (текст, опціональне)
7. **Особливі ознаки:**
   - Якщо користувач заповнив це поле — особливі ознаки **перезаписуються** у сутності Pet
   - При формуванні `search_text` для анкети використовуються оновлені особливі ознаки
   - Це дає можливість додати уточнення для пошуку без редагування тварини окремо

### 6.4 Вкладка "Активні пошуки"

- **Умова відображення:** Кнопка "Активні пошуки" з'являється у меню **тільки якщо** у користувача є хоча б один активний пошук
- **При натисканні:** Відображається **пагінований список** тварин, які зараз у пошуку:
  - Назва тварини
  - Статус
  - Кнопка для переходу до деталей
- **Деталі анкети пошуку:**
  - Інформація про тварину
  - Кнопки:
    - "Повернутись" — назад до списку активних пошуків
    - "Завершити пошук" — скасовує пошук (запитує підтвердження), очищає всі дані як описано в п. 2.5
    - "Переглянути рекомендації" — виводить першу рекомендацію з match_queue
  - Інформаційне повідомлення: "Тут ви можете переглядати рекомендації — потенційні знахідки вашої тварини"

### 6.5 Відображення рекомендацій (для власника)

- Виводиться одна анкета знахідки за раз
- Інформація для відображення:
  - Фото знайденої тварини
  - Опис (description з found_request)
  - Відстань до місця знахідки
  - **Дата створення анкети знахідки** (created_at)
  - Оцінка схожості (score)
- Кнопки:
  - "Наступна" — показує наступну рекомендацію
  - "Це моя тварина" — опізнання тварини
  - "Повернутись" — повернення до попереднього меню
- **Логіка при натисканні кнопок:** див. п. 6.1 (прибирання клавіатури з минулого повідомлення)

### 6.6 Відображення рекомендацій (для перехожого)

- Виводиться одна анкета пошуку за раз
- Інформація для відображення:
  - Фото тварини з профілю власника
  - Дані тварини (ім'я, порода, колір тощо)
  - Контактна інформація власника (якщо залишив)
  - Відстань
- Кнопки:
  - "Наступна" — наступна рекомендація
  - "Повернутись" — повернення (рекомендації стають недоступними)
- **Логіка при натисканні кнопок:** див. п. 6.1
- **Обмеження:** Показуються **тільки анкети з контактною інформацією** — анкети без контактів не виводяться

## 8. Сервіси

- **LostRequestService** — CRUD, пошук активних, скасування
- **FoundRequestService** — створення, отримання збігів з кешу
- **MatchingService** — асинхронний matching через івенти, розрахунок score
- **MatchQueueService** — управління чергою співпадінь
- **FinderRecommendationCache** — in-memory кеш для перехожих (HashMap з TTL)
- **FoundRequestCleanupJob** — крона для видалення анкет старших за 1 рік
